# 核心策略

本文件记录跨库、跨领域的 Python 性能优化方法论。具体库 API 和项目案例应分别写入 `libraries/` 与 `cases/`。

## 先测量，再优化

- **通用场景**: 准备优化某段代码，但尚未知道真实热点路径。
- **适用条件**: 任何性能优化开始前，尤其是多模块项目、调用链复杂或存在 I/O 与 CPU 混合开销时。
- **不适用/风险**: 不应把 profile 结果当成唯一真相；采样方式、输入数据和冷/热启动状态会影响结论。
- **推荐模式**: 先使用 `cProfile`、`viztracer`、`py-spy` 或业务内置指标定位热点，再选择优化手段。
- **验证方式**: 保存基线耗时、输入规模、运行参数和统计方法；优化后使用同一条件复测。

## 优先处理算法复杂度与数据结构

- **通用场景**: 热点函数中存在嵌套循环、重复扫描、线性查找、重复排序或不必要的数据转换。
- **适用条件**: 数据规模增长后耗时呈非线性上升，或 profile 显示大部分时间花在重复遍历上。
- **不适用/风险**: 小数据量下复杂结构可能增加常数开销；改变算法必须先证明输出语义一致。
- **推荐模式**: 在考虑微优化、并发或 C 扩展前，先检查时间复杂度和数据结构选择。
- **验证方式**: 用不同规模输入测试耗时曲线，并补充语义一致性测试。

## 消除重复计算

- **通用场景**: 相同输入或不变数据在热路径中被反复计算。
- **适用条件**: 计算结果可复用，输入可稳定标识，缓存生命周期和失效条件清晰。
- **不适用/风险**: 输入可变、缓存键不稳定、内存上限不明确或结果依赖外部状态时，缓存可能引入错误或泄漏。
- **推荐模式**: 对纯函数使用 `functools.lru_cache`；对大型结构使用显式缓存并设计容量、失效和并发策略。
- **验证方式**: 同时检查缓存命中率、内存占用和输出一致性。

## 将可预计算内容移出热路径

- **通用场景**: 循环体中反复执行相同或可预测的转换、解析、索引构建或中间表征生成。
- **适用条件**: 预计算成本能被多次复用摊薄，且预计算结果不会在循环中失效。
- **不适用/风险**: 一次性调用、输入频繁变化或预计算结果过大时，可能增加延迟和内存压力。
- **推荐模式**: 在循环外准备数组、字典、索引结构或中间表示，循环内只做查表、切片或轻量计算。
- **验证方式**: 对比“预计算成本 + 热路径耗时”和原始总耗时，并记录内存变化。

## 用性能数据约束优化范围

- **通用场景**: 存在多个可优化方向，但时间、人力或风险预算有限。
- **适用条件**: profile 能给出耗时占比，且每个方案可以估算收益与风险。
- **不适用/风险**: 只追逐局部热点可能忽略端到端延迟、内存、吞吐或可维护性。
- **推荐模式**: 优先处理高耗时占比、低语义风险、验证路径清晰的优化；保留未采纳方案和原因。
- **验证方式**: 用端到端指标确认局部优化没有转移瓶颈或破坏用户可见行为。
