# 向量化与数值计算

本文件记录跨库的向量化思想和数值计算优化原则。NumPy 具体 API 模式见 [`../libraries/numpy.md`](../libraries/numpy.md)。

## 使用批量运算替代 Python 逐元素循环

- **通用场景**: 对大量同构数据执行逐元素、逐行或逐组计算。
- **适用条件**: 数据可以表达为数组、列式结构或批量输入，且操作语义可以批量化。
- **不适用/风险**: 批量化可能增加临时数组、内存峰值或改变浮点运算顺序。
- **原始模式**:
  ```python
  result = []
  for a, b in zip(xs, ys):
      result.append(a + b)
  ```
- **推荐模式**:
  ```python
  result = xs_array + ys_array
  ```
- **验证方式**: 同时比较耗时、内存峰值和数值误差。

## 选择合适的向量化粒度

- **通用场景**: 全量向量化会产生过大的中间结果，或批量过小无法抵消转换成本。
- **适用条件**: 输入规模大，但可以按块处理并保持语义一致。
- **不适用/风险**: 分块会增加边界处理复杂度；过大批次会造成内存压力。
- **推荐模式**: 在“逐元素 Python 循环”和“一次性全量向量化”之间选择合适批大小。
- **验证方式**: 探索批大小与吞吐、内存峰值之间的关系。

## 使用编译工具处理难以向量化的热点循环

- **通用场景**: 热点循环存在状态依赖、分支复杂或无法用现有批量 API 表达。
- **适用条件**: 算法已经稳定，循环占用大量 CPU 时间，且编译工具支持相关数据类型。
- **不适用/风险**: JIT 编译有首次调用成本；Cython/Numba 可能增加构建、部署和调试复杂度。
- **推荐模式**: 在 profile 证明收益足够时，考虑 Numba、Cython 或专用原生扩展。
- **验证方式**: 区分首次编译耗时和热启动耗时，补充数值一致性测试。

## 避免为了向量化牺牲语义清晰度

- **通用场景**: 向量化改写明显提升速度，但代码难以理解或隐藏边界条件。
- **适用条件**: 优化位于核心热点，且可以通过命名、注释和测试保持可维护性。
- **不适用/风险**: 复杂向量化表达可能让后续修改更容易引入错误。
- **推荐模式**: 把复杂批量逻辑封装为小函数，并用测试覆盖边界输入。
- **验证方式**: 对空输入、单元素、极值、缺失值和 dtype 边界做一致性测试。
