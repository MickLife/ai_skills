# Loguru

本文件记录依赖 Loguru API 的日志性能优化模式。日志优化必须兼顾性能、可观测性和审计要求。

## 高频日志的性能成本

- **通用场景**: 热路径、循环或高并发请求中打印大量日志。
- **适用条件**: profile 或 I/O 指标显示日志格式化、锁竞争、写入或落盘占据明显耗时。
- **不适用/风险**: 不能为了性能随意删除审计、安全或故障诊断所需日志。
- **推荐模式**: 先度量日志开销，再选择采样、聚合、降级、异步写入或调整输出目标。
- **验证方式**: 对比日志开启/关闭、不同输出目标和不同日志量下的吞吐与尾延迟。

## 日志级别、采样与聚合输出

- **通用场景**: 每次迭代或每个请求都输出低价值状态日志。
- **适用条件**: 单条日志不是审计要求，且业务允许按周期或按比例输出。
- **不适用/风险**: 合规、计费、安全和问题追踪日志可能必须保留 INFO 或更高级别。
- **原始模式**:
  ```python
  for item in items:
      logger.info("Processing item {}", item.id)
      process(item)
  ```
- **推荐模式**:
  ```python
  for i, item in enumerate(items):
      if i % 100 == 0:
          logger.info("Progress: {}/{} processed", i, len(items))
      logger.debug("Processing item {}", item.id)
      process(item)
  ```
- **验证方式**: 确认日志量下降后仍能满足排障和审计需求；记录吞吐和 I/O 等待变化。

## 延迟格式化避免无效字符串构造

- **通用场景**: 低级别日志在生产环境关闭，但代码仍使用 f-string 或字符串拼接。
- **适用条件**: 日志参数构造本身有成本，且对应日志级别经常被过滤。
- **不适用/风险**: 如果参数表达式本身已经执行，延迟格式化不能消除这部分成本。
- **原始模式**:
  ```python
  logger.debug(f"item={item.id}, cost={cost_ms}ms")
  ```
- **推荐模式**:
  ```python
  logger.debug("item={}, cost={}ms", item.id, cost_ms)
  ```
- **验证方式**: 在 DEBUG 关闭的环境下测量热点路径耗时；避免在参数中调用昂贵函数。

## `enqueue=True` 的收益与限制

- **通用场景**: 日志写入目标较慢，希望减少业务线程被写 I/O 阻塞的概率。
- **适用条件**: 应用可以接受后台队列写入模型，并在退出时正确清理 logger。
- **不适用/风险**: `enqueue=True` 仍有队列、序列化和消费线程成本；日志量极大时可能出现积压或内存压力。Loguru 的 `logger.add()` 不应假设存在通用 `backlog` 参数。
- **推荐模式**:
  ```python
  from loguru import logger

  handler_id = logger.add("app.log", enqueue=True, rotation="100 MB", retention="7 days")
  try:
      run_app()
  finally:
      logger.remove(handler_id)
  ```
- **验证方式**: 观察队列积压、退出日志完整性、吞吐和尾延迟；确认异常退出时的日志丢失风险可接受。

## 可观测性要求下的日志优化边界

- **通用场景**: 日志优化和问题定位、审计或合规要求发生冲突。
- **适用条件**: 日志字段、级别和采样策略可以由业务负责人确认。
- **不适用/风险**: 只从性能角度下调日志级别可能让故障恢复成本上升。
- **推荐模式**: 将日志分为审计日志、错误日志、关键业务轨迹、调试轨迹和性能采样日志，分别设计输出策略。
- **验证方式**: 用真实故障排查流程检查优化后日志是否仍能定位问题。
