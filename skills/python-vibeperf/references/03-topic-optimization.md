# 专题迭代与总结

## 目标

本阶段的目标是针对 02 阶段识别出的各个性能瓶颈专题，逐个进行“需求拆解 -> 迭代落地 -> 效果总结”的完整循环。通过按专题分目录的产物结构，确保每个专题的优化过程清晰、可追溯，并通过小步快跑的子需求迭代控制重构风险。

## 过程与规则

**状态管理：**

- 提示用户指定先进行哪个专题的优化（专题序号使用 A, B, C...）。
- 进入本阶段时，更新 `docs/perf/rounds/<timestamp>/PROGRESS.md`，将当前专题的状态标记为“进行中”。
- 完成当前专题的所有步骤（拆解、迭代、总结）后，更新 `PROGRESS.md`，将该专题标记为“已完成”，并汇总最终的性能提升数据。
- **循环机制**：当前专题完成后，提示用户选择下一个专题，重复本阶段的所有步骤，直到所有专题优化完毕。

对于每个选定的专题，必须完整执行以下 3 个步骤：

### 步骤 1：专题需求拆解

1. **识别当前专题的优化方向与 ROI 评估**
   - **读取并执行 `brainstorming` 技能**：使用 Read 工具读取系统可用技能列表中的 `brainstorming` 技能文档，并严格遵循其指令。
   - 基于当前专题的瓶颈分析报告（`BOTTLENECK-{A,B,C...}-{name}.md`），与用户探讨多种可能的解决思路，评估每个优化方向的投入产出比（ROI）和潜在风险。
2. **拆解子需求**
   - 将优化方向拆解为具体的、可执行的子需求。
   - 明确每个子需求的目标、预期成果和优先级。
3. **生成需求文档**
   - 将拆解结果输出为 `01-REQUIREMENTS.md`。

### 步骤 2：子需求迭代闭环

对于步骤 1 拆解出的每一个子需求，必须按顺序执行以下闭环，并按产生顺序加上数字前缀和子需求名称后缀（例如：`02-SOLUTION_DESIGN-<sub_req_name>.md`, `03-OPTIMIZATION_EXECUTION-<sub_req_name>.md` 等）：

1. **实验与设计**
   - **查阅知识库**：在设计方案之前，必须使用 Read 工具读取 `skills/python-vibeperf/knowledge/INDEX.md` 并查阅相关分类文档，结合知识库中的成熟模式进行方案设计。默认只读取 `cases/README.md` 的案例摘要索引；只有当前子需求与某个案例高度相似或需要核验证据时，才读取单个案例正文。
   - **读取并执行 `brainstorming` 技能**：与用户探讨当前子需求的优化方案，确认实验的基础假设和预期目标。
   - 执行代码实验，验证方案的可行性，请求用户拍板最终选型。
   - **读取并执行 `writing-plans` 技能**：将收敛的讨论结果写成严谨的设计文档（`XX-SOLUTION_DESIGN-<sub_req_name>.md`）。
2. **执行与测试**
   - **读取并执行 `executing-plans` 技能**：严格按照设计方案执行代码修改。
   - **读取并执行 `test-driven-development` 技能**：在修改原有逻辑前必须先写好测试用例，确保优化前后的输出一致性。
3. **审查与验证**
   - **读取并执行 `requesting-code-review` 技能**：审查代码，检查是否引入了死锁、内存泄漏等问题。
   - 验证优化效果：在不使用 VizTracer 的情况下正常运行性能测试，记录真实性能指标。
   - **Fallback 机制**：仅在测试失败或性能未达标时，**读取并执行 `systematic-debugging` 技能**寻找根因。
4. **提交与记录**
   - **读取并执行 `verification-before-completion` 技能**：确保性能测试全绿后，直接进行本地 Git 提交。
   - 记录当前子优化的执行情况和性能提升数据，输出为 `XX-OPTIMIZATION_EXECUTION-<sub_req_name>.md`。

### 步骤 3：输出专题优化报告

当前专题的所有子需求均迭代完成后：
1. **对比基线数据**
   - 收集当前专题优化后的整体性能数据。
   - 与 01 阶段的基线数据进行对比，量化该专题带来的整体性能提升。
2. **生成报告**
   - 总结该专题的优化经验、遗留问题和未来建议。
   - 输出该专题的专属优化报告，按顺序加上数字前缀（如 `XX-OPTIMIZATION_REPORT.md`）。

---

**约束条件：**
- 必须基于当前专题瓶颈分析结果进行需求拆解。
- 必须通过代码实验和测试用例验证每个子需求的可行性和正确性。
- **严禁跨专题或跨子需求并行执行**：必须完成当前子需求的闭环后，才能开始下一个子需求；必须完成当前专题的报告后，才能开始下一个专题。

## 输出产物

在 `docs/perf/rounds/<timestamp>/03-topic-optimization/topic-{A,B,C...}-{name}/` 目录下，按顺序生成：

- `01-REQUIREMENTS.md`：当前专题的需求拆解文档。
- `02-SOLUTION_DESIGN-<sub_req_name1>.md`：子需求 1 的设计文档。
- `03-OPTIMIZATION_EXECUTION-<sub_req_name1>.md`：子需求 1 的执行结果文档。
- `04-SOLUTION_DESIGN-<sub_req_name2>.md`：子需求 2 的设计文档。
- `05-OPTIMIZATION_EXECUTION-<sub_req_name2>.md`：子需求 2 的执行结果文档。
- `06-OPTIMIZATION_REPORT.md`：当前专题的最终性能优化报告。
