# 分析方法

## 1. 侦察

运行 `scripts/scan_tree.py`：

- 统计 Python/C/C++ 文件、行数和近似 token。
- 识别 `pyproject.toml`、CMake、Meson、Bazel、Make 等构建入口。
- 根目录存在一个 `.git` 时按单仓处理；兄弟目录各有 `.git` 时进入多仓模式。
- 找出 `main.py`、`__main__.py`、`main.cpp`、可执行 target 等入口线索。

默认每个分析单元不超过约 100k 输入 token。预计规模远超上下文时，先询问用户是否缩小范围、指定入口或改用 `overview`。

## 2. 分解

运行 `scripts/deps_scan.py`，以目录边界和依赖关系划分模块：

- 合并小且紧密相关的目录。
- 超预算模块继续按子目录/依赖簇拆分，标记 `needs_split`。
- 最终写 `module_tree.json`，记录文件、token、入/出依赖和子模块。

### 入口模式

运行 `scripts/find_entry.py` 定位入口，然后：

1. 前向追踪入口使用的 import/include 文件。
2. 反向找出直接调用或引用入口的文件。
3. 只分析这个相关文件集合；把范围外顶层模块列入“未分析部分”。
4. 写 `entry-trace.json`，记录根、相关文件和裁剪理由。

静态依赖不等于完整调用关系。动态导入、虚函数、函数指针、宏、插件注册无法确认时必须标为未知。

## 3. 深挖

叶子模块优先。每个模块记录：

- 一句话职责。
- 输入、输出、来源、去向和数据形态。
- 关键类型/函数及 `path:line`。
- 主要运行路径、状态变化、并发方式、错误处理和资源生命周期。
- 依赖谁、谁依赖它，以及证据。
- 无法确认的设计点和原因。

有子代理能力时可并行分析独立模块，但每个代理只写独立事实摘要；主代理统一合成文档，避免多人写同一文件。

## 4. 合成

顺序不可反：

1. 先提炼系统边界、黑盒输入输出、核心概念、处理阶段和质量约束。
2. 再按 `architecture-views.md` 选择真正需要的图。
3. 章节按 `output-format.md` 裁剪；空章节直接删除。
4. 复杂模块按 `submodule-section.md.tmpl` 拆到 `docs/modules/`，主文档保留摘要与链接。
5. 每张图保存 `.mmd`；根据 `render-manifest.json` 选择 SVG 或 Mermaid 围栏。
6. 写 `metadata.json`，包括模式、入口、仓库、视图、拆分模块、渲染模式。

## 5. 失败与降级

- 未识别构建系统：按目录和静态 import/include 分析，并说明限制。
- C/C++ 缺少 `compile_commands.json`：不声称拥有完整调用图。
- Mermaid 渲染器缺失/失败：保留 `.mmd`，改用 Mermaid 围栏，不引用 SVG。
- 阅读器不显示图：设计意图与关键解读必须足以替代图。
- 非主语言模块：记录其边界和对外关系，不深入猜测内部设计。

## 6. 质量门

- 结论可追溯到代码或用户上下文；未知内容明确标记。
- 入口模式没有悄悄退化为全仓摘要。
- 视图均有设计意图和关键解读，且顶层节点不超过 9 个。
- 长路径/类名没有放入宽 Markdown 表格。
- 所有本地链接和图像存在；围栏闭合；无残留占位符。
- `validate_markdown.py` 返回成功。
