# 多仓库分析

## 识别与清点

根目录下多个兄弟目录各有 `.git`，或用户明确提供多个仓库时进入多仓模式。所有节点 ID 和证据路径必须带仓库名，避免同名模块冲突。

对每个仓库记录：

- 名称、路径、主要语言、构建系统。
- 角色：共享约定/头文件、核心库、服务、工具、绑定层等。
- 入口和公共接口。

写 `repo_inventory.json`。

## 扫描顺序

1. 共享 schema、头文件、协议和接口。
2. 被多个仓库依赖的核心库。
3. 服务和可执行程序。
4. 工具、脚本和非主语言仓库。

先分析被依赖方。每仓只把公共接口、导出符号、职责和主要风险的紧凑摘要带到下一仓，避免上下文膨胀。

## 跨仓关系

寻找并引用源行：

- Python 包的跨仓 import、editable install。
- C/C++ 共享头和库链接。
- CMake `add_subdirectory`、`FetchContent`、`find_package`。
- Bazel 外部仓库和跨仓 target。
- Python 通过 pybind11/cffi/ctypes 调用 C/C++。
- 多仓共同使用的 schema、消息名或协议文件。

代码只能证明依赖存在，不能证明业务语义时，明确写“无法从代码中提取”。

## Markdown 输出

多仓视图按需包含：

- 仓库角色清单（短字段可用表格）。
- 仓库级依赖图。
- 每条跨仓关系的分段说明：来源、目标、关系、证据。
- 共享约定由谁定义、谁使用。
- 修改共享约定后的重建顺序。

长路径、构建 target 和符号名不要塞入宽表格。
