# 架构视图与抽象提炼指南

本文是 `codebase-architect` 的设计表达核心，解决两件事：

1. **如何从代码提炼架构级抽象**（而不是浮于代码表面的逐文件罗列）。
2. **如何为每种设计意图选择合理的视图/图表**（4+1 视图及子视图、UML、DFD、泳道图），以及对应的 Mermaid 表达方式。

> 原则：**先有抽象，再选视图，最后画图。** 图是抽象的表达，不是目的。只画"读者理解架构真正需要"的图，不为凑格式堆图。

---

## 一、从代码提炼架构级抽象

设计文档的价值在于"提炼"。阅读代码时，主动回答下面几组问题，把答案作为文档的骨架。

### 1. 系统边界与外部参与者（谁在用它、它连接谁）

从这些线索识别系统"对外的脸"：

- 入口：`main`、CLI 命令、`__main__`、服务端点（FastAPI/Flask 路由、gRPC service）、库的公共 API。
- 输入/输出边界：文件读写、网络、数据库、环境变量、标准输入输出、进程间通信、跨语言调用边界。
- 谁调用它、它调用谁（进程外）。

产出：一张**系统上下文图**（谁给它输入、它给谁输出）。

### 2. 系统级输入 / 输出（黑盒 I/O 契约）

把整个系统当黑盒，提炼：

- **输入**：来源、数据形态/契约（结构体、schema、协议、文件格式）、约束。对应代码：入口参数、配置加载、反序列化点。
- **输出**：去向、形态、副作用（写文件、发消息、改状态）。对应代码：返回值、序列化点、写 IO 点。

产出：输入表 + 输出表，每行附 `file:line`。这是"整架构级抽象"的起点。

### 3. 核心领域概念 / 数据抽象

不是罗列所有类，而是提炼**支撑系统的少数核心概念**：

- 核心数据结构、领域实体、关键类型、schema、状态枚举。
- 它们之间的关系（组合、聚合、继承、引用）。
- 判据：删了它系统就说不清楚的，才是核心。

产出：**领域模型类图**或 **ER 图**（只含核心实体）。

### 4. 关键处理阶段 / 管道（从控制流提炼）

顺着主入口追主控制流，把"输入 → 输出"的过程抽象成有限个**处理阶段**（stages / pipeline），每阶段一句话职责。

产出：处理阶段流水图 + 每阶段涉及的模块。

### 5. 质量属性与约束（从代码推断，附证据）

- 并发模型（线程/进程/协程/锁）、性能相关设计（缓存、批处理、零拷贝）、可靠性（重试、超时、降级）、可扩展性（插件、注册表、策略）。
- 平台/二进制兼容(ABI)/依赖/兼容性约束。

产出：质量属性清单，每条附代码证据。

### 6. 关键设计决策与权衡

识别代码里体现的**有意设计**：分层、设计模式（工厂/策略/观察者、C++ 的 RAII 资源管理等惯用法）、抽象边界、依赖倒置。推断其动机与代价。

产出：设计决策表（决策 / 动机 / 取舍 / 证据）。

### 7. 诚实标注：提炼不出来就不要编

上面每一类抽象，都可能出现"代码里看不出来"的情况——尤其是**设计意图、非功能目标、历史约束、外部契约的语义**这类需要人或外部文档才能确认的内容。此时的铁律：

- **禁止推测、禁止凭经验补全、禁止用行业惯例假装是本项目的设计。** 一句看似合理实则没有依据的话，会污染整份设计文档，比留白危害更大。
- 在对应位置**显式标注"无法从代码中提取"**：
  - 行内：`<span class="badge unknown">无法从代码中提取</span>`
  - 成块：`<div class="callout-unknown">…说明缺口…</div>`
- 标注时尽量写清三件事：**缺什么**（哪个设计点）、**为什么判定不了**（代码中无相关证据/仅有实现无意图/契约在外部）、**建议的确认途径**（问哪个角色、看哪份外部文档、跑什么实验）。
- 若用户提供了额外上下文（需求文档、口头说明），可据此补全，但要注明来源是"用户提供的上下文"而非代码。
- 区分"确有其事但未展开分析"（→ 归入"未分析部分"）与"无法从代码判定"（→ 标注"无法从代码中提取"），二者不要混为一谈。

判据速记：**能指到 `file:line` 才写成结论；指不到就标注为无法提取。**

## 二、4+1 视图模型（Kruchten）

用不同视图服务不同读者。每个视图选它擅长表达的子图。

| 视图 | 关注 | 读者 | 典型 UML 子视图 | 本 skill 的 Mermaid 表达 |
|---|---|---|---|---|
| **逻辑视图** Logical | 系统提供的功能、领域结构 | 终端用户/分析 | 类图、状态图 | `classDiagram`、`stateDiagram-v2` |
| **进程视图** Process | 运行时、并发、通信、性能 | 集成/性能 | 时序图、活动图、通信图 | `sequenceDiagram`、`flowchart`（活动）、泳道 |
| **开发视图** Development | 代码组织、模块/包、依赖 | 程序员 | 包图、组件图 | `flowchart` + `subgraph`（分层/分包） |
| **物理视图** Physical | 部署拓扑、产物、连接 | 系统工程 | 部署图 | `flowchart`（节点=环境/主机/进程/库） |
| **场景（+1）** Scenarios | 关键用例，驱动并验证架构 | 全体 | 用例图 | 场景表 + `flowchart` 近似用例 |

选型建议：

- **库 / SDK / CLI**：逻辑 + 开发 + 场景为主；物理视图可精简或标注"单进程，不适用"。
- **服务 / 多进程 / 分布式**：五视图齐全，重点在进程视图与物理视图。
- **数据处理 / 编译器 / 管线**：进程视图 + DFD 为主，配逻辑视图讲数据模型。

## 三、DFD 数据流图（数据流向图）

DFD 表达"数据如何流动与加工"，**没有控制流**（无判定、无循环）。四种元素：

| 元素 | 语义 | Mermaid 近似 |
|---|---|---|
| 过程 Process | 把输入变换成输出（动词短语） | 圆/圆角：`P((1 加工))` |
| 数据流 Data flow | 信息流动（命名，带方向） | 箭头 `-->|数据名|` |
| 数据存储 Data store | 存放数据供后续使用（名词复数） | `D1[( 存储 )]` |
| 外部实体（外部系统/角色） | 系统外的数据来源/去向 | 方框 `E[外部实体]` |

分层规则（保持编号一致）：

- **上下文图**：唯一一个过程代表整个系统 + 所有外部实体。
- **0 层**：把系统拆成 3~9 个过程（编号 1、2、3…）。
- **1 层**：过程 1 细化为 1.1、1.2…；数据存储在首次出现的最高层显示。
- 每个数据存储至少要有输入流和输出流（可能在不同层）。

Mermaid 约定（本 skill 统一配色）：

```
flowchart LR
    ext[外部实体]:::ext -->|输入流| P1((1 加工)):::proc
    P1 -->|中间数据| D1[( D1 存储 )]:::store
    D1 --> P2((2 加工)):::proc
    P2 -->|输出流| ext
    classDef ext fill:#FBEFE0,stroke:#C0603A;
    classDef proc fill:#F3E2CE,stroke:#CC8A2E;
    classDef store fill:#FFF9F1,stroke:#9B8A79;
```

何时用 DFD：数据加工/转换是系统本质时（ETL、编译器、图像/信号处理、批处理管线）。纯请求-响应服务优先用时序图。

## 四、UML 视图与 Mermaid 映射

| UML 图 | 用途 | Mermaid |
|---|---|---|
| 类图 Class | 领域模型、类关系 | `classDiagram`（`-->` 关联、`*--` 组合、`o--` 聚合、`<|--` 继承） |
| 状态图 State | 对象/会话状态迁移 | `stateDiagram-v2` |
| 时序图 Sequence | 对象/进程间时间序交互 | `sequenceDiagram`（天然按 participant 分泳道） |
| 活动图 Activity | 流程/算法步骤（可含判定） | `flowchart TD`（`{判定}`） |
| 组件图 Component | 组件与接口 | `flowchart` + `subgraph` |
| 包图 Package | 包/命名空间组织 | `flowchart` + `subgraph` 嵌套 |
| 部署图 Deployment | 节点与产物拓扑 | `flowchart`（节点=主机/进程/库） |
| 用例图 Use case | 参与者与用例 | 场景表为主；`flowchart` 用 `(用例)` 圆角 + 参与者方块近似 |

关系记法速记（类图）：

```
classDiagram
    Base <|-- Derived      %% 继承
    Owner *-- Part         %% 组合（强生命周期）
    Club o-- Member        %% 聚合（弱）
    A --> B                %% 关联/依赖
    A ..> C : uses         %% 依赖
```

## 五、泳道图（Swimlane）

泳道图 = 活动图 + 按"负责人/组件/角色"分道，强调**职责边界**与**跨角色流转**。

两种 Mermaid 表达，按场景选：

1. **flowchart 分道**（表达职责归属 + 分支流程）：

```
flowchart TB
    subgraph 调用方
      a1[发起请求] --> a2[处理响应]
    end
    subgraph 服务核心
      b1[校验] --> b2{是否命中缓存}
      b2 -->|是| b3[返回缓存]
      b2 -->|否| b4[计算]
    end
    subgraph 存储
      c1[(数据库)]
    end
    a1 --> b1
    b4 --> c1
    b3 --> a2
    b4 --> a2
```

2. **sequenceDiagram**（表达时间序 + 消息往返）：每个 participant 即一条泳道，适合请求-响应、协议交互。

选型：强调"谁负责哪一步 + 有分支判定" → flowchart 泳道；强调"时间先后 + 消息往返" → 时序图。

## 六、视图选型决策速查

按"你要表达什么"倒推该画什么：

| 你要表达 | 首选视图 | Mermaid |
|---|---|---|
| 系统对外的输入输出 | 系统上下文图 / DFD 上下文 | `flowchart` |
| 领域里有哪些核心概念 | 逻辑视图·类图 | `classDiagram` |
| 一次调用在运行时怎么走 | 进程视图·时序图 | `sequenceDiagram` |
| 谁负责哪一步、带分支 | 泳道图 | `flowchart`+`subgraph` |
| 数据如何被逐级加工 | DFD 分层 | `flowchart` |
| 代码怎么分层分包 | 开发视图·组件/包图 | `flowchart`+`subgraph` |
| 有状态对象怎么迁移 | 逻辑视图·状态图 | `stateDiagram-v2` |
| 部署在哪、连什么 | 物理视图·部署图 | `flowchart` |
| 关键用例有哪些 | 场景视图 | 场景表(+`flowchart`) |

## 七、Mermaid 语法自检清单

写入 HTML 前逐条核对，避免渲染失败：

- 含空格/特殊字符的节点文字加引号：`A["含 (括号) 的标签"]`。
- 不要用保留字 `end` 作节点 id（大写 `End` 或换名）。
- `classDiagram` 泛型写 `List~T~`，不要裸 `<>`。
- 子图语法：`subgraph 名称` … `end`，`end` 单独一行。
- `sequenceDiagram` 的 participant 别名：`participant X as 显示名`。
- 一个 `<pre class="mermaid">` 只放一张图。
- 配色统一用本文 `classDef`（赤陶/琥珀/暖白），与页面主题一致。
- **单图复杂度上限**：流程/DFD/组件图顶层节点经验上 ≤ 9 个；超了就分层（拆上下文图/0 层/1 层）或按簇拆 `subgraph`，否则会糊成一团、失去表达力。
- **图必配文字**：每张图前用文字讲清"这张图要表达什么设计意图"，图后用 `<p class="diagram-note">` 给关键点解读。孤立堆图＝没提炼。

## 八、章节与视图的组织建议

不是每个项目都要全部视图。总原则：先写**架构级抽象章**（I/O、核心概念、处理阶段、质量属性，这是灵魂），再按 4+1 补充读者需要的视图（能省则省），复杂模块在"子模块详细设计"章展开（`submodule-section.html.tmpl`）。

具体的章节菜单、必写/按需裁剪、动态编号规则是单一事实源，见 `output-format.md`。
